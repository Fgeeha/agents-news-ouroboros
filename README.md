# agents-news-ouroboros

Новостной конвейер экспертов, целиком построенный на
[Ouroboros](https://github.com/razzant/ouroboros) и его CLI: каждая роль
конвейера — отдельная headless-задача `ouroboros run`, расписание — cron
Ouroboros, история и логи — `ouroboros tasks` и `ouroboros logs`. Никакого
web- или desktop-интерфейса в проекте нет, всё из терминала через `make`.
Самостоятельный аналог [agents-news](https://github.com/Fgeeha/agents-news)
с той же логикой конвейера, но без шлюза LiteLLM и OpenAI-клиента.

## Что делает конвейер

RSS-ленты → дедупликация (id, Жаккар по словам, подтверждение gate-ролью в
серой зоне) → поиск **ракурса** («можно ли переписать новость для этой
аудитории и почему») → эксперт пишет статью вокруг ракурса → независимый
редактор сверяет её с исходником и ставит вердикт → markdown в
`out/<дата>/<эксперт>/`, отклонённое повторно — в `rejected/`.

Аудитории задаются в `config.yaml` (`experts`): агрономия, IT, медицина,
экономика, право, образование, стройка, энергетика, транспорт, культура,
экология.

## Пример результата

Реальный прогон 2026-09-03 (`make run-once`, лента Habr, эксперт `it`): три
задачи Ouroboros — ракурс, статья, рецензия — около 7 минут на CPU-инференсе,
файл `out/2026-09-03/it/исследователи-разместили-фальшивое-объявление-о-сдаче-кварти.md`:

```markdown
---
source: https://habr.com/ru/news/1077916/
expert: it
expert_model: ouroboros
reviewer_model: ouroboros
verdict: ПРИНЯТО
revisions: 0
date: 2026-09-03
---

# Исследователи разместили фальшивое объявление о сдаче квартиры на Даунинг‑стрит на Booking.com

> Ракурс: реальный кейс уязвимости в платформе с транзакциями …

## Замечания рецензента

1. **Фактология:** все факты из исходника корректно отражены в статье …
```

Новости без ракурса аудитория не получает: в том же прогоне по ленте
Lenta.ru gate-роль отказала и `agro`, и `it` с внятной причиной, статей не
создано.

## Как участвует Ouroboros

| Что | Как |
|---|---|
| Вызов модели (ракурс, статья, рецензия, доработка, подтверждение дубля) | `ouroboros run --jsonl --quiet --memory-mode empty --timeout 600 --disable-tools <список> "<промпт>"` из `llm.py` |
| Ответ модели | последний объект `final` в jsonl-потоке, поле `result.result` |
| Расписание | `make schedule CRON="0 6 * * *"` → `ouroboros schedule add` с промптом из `prompts/run.md` |
| История, логи, состояние | `make tasks`, `make logs`, `make status` |

Промпты ролей — те же, что в agents-news; системный и пользовательский
склеиваются в один текст задачи. Инструменты агенту отключены
(`prompts/disable-tools.txt`, список из документации Ouroboros), память
пустая — задача сводится к чистому текстовому ответу.

Код возврата `ouroboros run` не используется: на локальном стеке он равен
`1` даже у успешной задачи (приёмочное ревью деградирует без облачных
моделей). Источник истины — `final.result.status`. Код `2` означает, что
сервер недоступен: конвейер останавливается с понятной ошибкой.

### Ограничения, вытекающие из Ouroboros

- **Одна модель на все роли.** Ouroboros берёт модель из своей настройки
  `OUROBOROS_MODEL`, per-task выбора в CLI нет. Поэтому независимость
  рецензента «другим семейством моделей», как в agents-news, здесь не
  обеспечивается; поля `expert_model`/`reviewer_model` во frontmatter —
  имена ролей.
- **Нет эмбеддингов.** Дубли между сайтами ищутся только по совпадению
  значимых слов заголовка плюс подтверждение gate-ролью; пересказы одного
  события разными словами не склеиваются.
- **Каждый вызов — задача со своей финализацией** (десятки секунд
  накладных расходов сверх инференса). На CPU одна новость на 11 аудиторий
  занимает десятки минут.

## Быстрый старт

Нужны [uv](https://docs.astral.sh/uv/) и `ouroboros` в `PATH` с запущенным
сервером (`make status` должен ответить). Провайдер модели настраивается в
самом Ouroboros:

```bash
ouroboros settings set OPENAI_COMPATIBLE_BASE_URL http://127.0.0.1:4000/v1
ouroboros settings set OPENAI_COMPATIBLE_API_KEY <ключ шлюза>
```

`http://127.0.0.1:4000` — это `make bridge`: runtime Ouroboros строит
HTTP-клиент с `trust_env=False`, поэтому self-signed сертификат шлюза
LiteLLM ему не подсунуть ни через `SSL_CERT_FILE`, ни через системное
хранилище, а nginx перед шлюзом маршрутизирует по заголовку `Host`. Мост
(`bridge.py`, stdlib) принимает http на localhost, подставляет `Host` и
проверяет сертификат по `certs/litellm.home.arpa.pem`. Если шлюз доступен
по обычному https или http — мост не нужен, укажите его адрес напрямую.

```bash
make install
make bridge                  # терминал 1: мост к шлюзу (если нужен)
make status                  # сервер Ouroboros отвечает
make run-once                # одна новость, без состояния
make run LIMIT=3             # боевой прогон, не больше 3 новостей
make schedule                # каждый день в 06:00 Europe/Volgograd
make tasks                   # задачи Ouroboros: роли и cron-прогоны
make test                    # тесты (без сети и Ouroboros)
```

Cron-задача — это тоже агент Ouroboros: по промпту из `prompts/run.md` он
выполняет `make run` в каталоге проекта и возвращает итоговую строку лога
`Готово: обработано N новостей, создано M статей, …`. Путь и лимит
подставляются в промпт при `make schedule`, потому что у `schedule add`
нет `--workspace`.

## Структура

```
Makefile                          # все операции; секция «Расписание Ouroboros»
prompts/run.md                    # промпт cron-задачи
prompts/disable-tools.txt         # инструменты, отключаемые у ролей
config.yaml                       # параметры Ouroboros и моста, ленты, эксперты
src/agents_news_ouroboros/
  llm.py                          # OuroborosCLI: роль -> ouroboros run
  bridge.py                       # http-мост localhost -> https-шлюз для провайдера Ouroboros
  report.py                       # разбор jsonl-потока, сводка, код возврата
  main.py, feeds.py, pipeline.py  # конвейер
tests/                            # офлайн-тесты: конвейер, разбор, CLI-обёртка, мост
docs/superpowers/specs/           # проектная спецификация
```
